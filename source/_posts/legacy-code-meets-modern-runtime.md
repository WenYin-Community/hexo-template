这个月连着做了三次"老代码搬家"：2003 年的 Discuz! 2.5 SP1（GBK 编码，125 个 PHP 文件）、跑了多年的 Discuz 4.1 论坛（PHP 8.5 移植 + 安全加固），以及一个 Delphi 7 写的、给 Windows 95 用的 AI 聊天客户端。

三套技术栈，年代跨度二十年，但踩的坑出奇地同构：**真正要命的不是语法报错，而是那些"写完那一刻是对的、换了环境之后默默变味"的写法**。语法错误至少会告诉你哪一行；静默失效只能靠对比和实测去挖。

本文按问题类型整理，每一条都附上具体的错误信息和修法。

## 一、三套环境，同一条纪律

改代码之前先把运行栈搭起来，否则后面每改一处都分不清是"改错了"还是"环境没搭对"。

- **Discuz! 2.5**：podman 起 php-fpm 8.5 + MySQL 5.7 + nginx，代码挂进去。两个前置确认：镜像里必须已编译 `mysqli`、`iconv`、`mbstring`、`gd`，且 `short_open_tag=On`（这套源码里大量 `<?` 短标签）；数据库的 `sql_mode` 要清空，否则严格模式下老代码那些"缺列 INSERT"会直接失败。
- **Discuz 4.1**：同一套栈，但目标是"先修线上报错，再做安全加固"，所以基线必须能从生产 dump 还原。
- **Delphi 7**：本机没有编译器，只能在 KVM 的 Windows 里装 Delphi 7，按 Ctrl+F9 编译。

纪律是同一条：**分阶段提交**（阻断项 → 告警治理 → 加固 → 建库 → 验证），每个阶段单独回退。

## 二、几百处裸下标：工具能改，但工具本身要验

最开始的症状很直接：Discuz 2.5 **每个 GET 请求都致命**，首页都起不来。

```
Fatal error: Uncaught TypeError: extract(): Argument #1 ($array)
must be of type array, false given
```

根因在引导层：一个转义函数对空数组返回了 `false`，调用方拿去做 `extract()`。PHP 8 里 `extract(false)` 直接致命。

但这个库真正的硬骨头在别处：**全站 841 处裸数组键**，分布在 46 个文件里，其中 **572 处藏在双引号字符串内**。

`$var[key]` 在 PHP 5 里会被宽容地当成字符串键，PHP 8 把它当未定义常量，直接报错。

**这里千万别用正则批量替换。** 裸键和字符串字面量长得一模一样，正则会误伤注释和用户文本。正确做法是用 PHP 自己的 tokenizer 写一个只认"数组下标位置"的改写器。

然后我多踩了一步：第一版改完 lint 干净，第二版想更精确，结果**反而改坏了 9 个文件**——因为 PHP 8 的简单插值只支持一个下标，而带引号的下标在简单插值里本身就构成解析错误。最后只能按第一版重建。

同类问题在 Discuz 4.1 里换了张脸：**复杂插值 `{$arr[key]}`** 的裸键在 PHP 8 被当常量，报 `Undefined constant "fid"`。注意它和简单插值 `$arr[key]` 语义不同——后者才是字符串键。两种写法只差一对花括号。

这里还有两个连带教训：

- 静态扫描器最初把"双引号字符串内的下标"整个排除了（因为简单插值确实安全），结果漏掉了复杂插值这一类。**这个问题是靠端到端遍历页面抓出来的，不是扫出来的。**
- 批量加引号时用的是"匹配最内层键"的正则，嵌套结构会漏：`{$GLOBALS[lang]['page']}` 的外层 `lang` 依然是裸键。复验时扫描器其实报了这处，被我当噪音略过了——**扫描器的输出不要随手忽略**。

## 三、同一个函数，两处要相反的参数

`extract()` 在两个地方需要完全相反的参数。

`post.php` 用 `EXTR_SKIP` 是对的——提取的是新变量，不覆盖已有值。但登录那段（`logging.php`）**必须用 `EXTR_OVERWRITE`**：因为引导层里已经存在 `$adminid`、`$groupid`、`$discuz_uid` 这些全局变量，用 `EXTR_SKIP` 的话新值根本进不去。

症状是"登录不报错，但就是不生效"。

而且这段的致命错误只在**登录失败**时触发——`fetch_array` 返回 `null`，再喂给 `extract()`。正常登录流程测不出来，必须专门测错误路径。

## 四、有些"坏代码"是有意的

Discuz 2.5 的缓存模块里有个 `array_del()`，读起来像是坏的：它对数组调 `trim($f)`，条件恒为假，所以**从来没有删除过任何键**。

但站里的欢迎短消息、版规恰恰依赖这些键留在缓存中。这个"空实现"是功能的一部分。修法只消除 TypeError、行为原样保留，并在代码里写清原因——否则下一个人会"好心"把它修成真的删除。

类似的还有模板里一处漏了 `$` 的裸常量，在 PHP 5 下被当成字符串真值，改"对"了反而会变行为。

**判断标准**：如果一个"bug"已经存在了二十年而功能正常，先假设它是特性，再去找证据。

## 五、一个赋值，让所有数据库错误变成白屏

这是这个月最贵的一条，值得单独讲。

Discuz 4.1 的数据库层里有一行看着很正常的代码：

```php
$this->conn->report_mode = MYSQLI_REPORT_OFF;
```

意图很清楚：关掉 mysqli 的异常模式，让错误走框架自己的 `halt()` 优雅提示。

问题是，**`report_mode` 根本不是 mysqli 的属性**。这行只是给对象动态加了个属性，PHP 8.2 起还会给一条弃用警告，行为上是彻头彻尾的空操作。

而 PHP 8.1 之后的 mysqli **默认就是抛异常模式**，且 `@` 抑制无效。于是：

- 数据库连不上 → 未捕获异常 → 白屏；
- SQL 出错 → 未捕获异常 → 白屏；
- 本该显示"数据库暂时不可用"的页面，变成一张没有任何信息的白屏。

正确写法只有一种：

```php
mysqli_report(MYSQLI_REPORT_OFF);
```

**这条坑最贵的地方在于它有"假证据"**：生产目录的错误日志里堆了 **4186 条**记录，看起来像"数据库连接一直有问题"。实际上那些全是白屏被记录下来的结果，不是原因。修完之后数字立刻归零。

教训：看到一个"配置项"，先确认它真的是那个库的属性/选项，而不是同名的动态属性。

## 六、GBK 是全程的约束

老系统用 GBK，这个约束会出现在四个完全不同的地方。

**1. 写回文件会被截断。** 用 utf-8 或 latin-1 去读写含中文的 PHP 文件，会出现编码失败甚至文件被截断。正确姿势是从 git 基线恢复，用 GBK 往返（先解码再编码）重做。

**2. 数据库连接要显式设字符集。** 重写数据库层时保留 `SET NAMES gbk`，否则取出来的中文全是问号。

**3. 界面全是方块。** 查了两层：第一层是响应头写 `charset=UTF-8` 而正文是 GBK，浏览器按头解码全变替换字符；第二层更隐蔽——初始化数据库时把安装 SQL 按 UTF-8 写进了 GBK 库，于是"游客""管理员"这些初始数据本身就是错的字节。用 GBK 字节重新导入才干净。

**4. GBK 的尾字节可能是反斜杠。** 这一条在 Delphi 客户端上炸的：某几个汉字的 GBK 编码第二个字节是 `0x5C`（`\`），旧的手写逐字节 JSON 转义会把它当转义符，**直接破坏消息、产出非法 JSON**。

修法是按 Windows 的 `ByteType` 识别双字节字符、整字跳过，而不是逐字节处理：

```pascal
// 伪代码：遇到 GBK 双字节字符时整体前进 2 字节
if ByteType(s, i) = mbLeadByte then Inc(i, 2) else Inc(i, 1);
```

## 七、跑得起来但会出事的地方

**`char(32)` 装不下 bcrypt。** 老库密码列是 md5 的长度，升级到 bcrypt 后 60 个字符会被**静默截断**。症状极迷惑：第一次设置密码能登录成功，第二次就失败。修法是列宽改 `varchar(255)`，新密码用 `password_hash()`，历史 md5 在登录成功后自动升级。

**`TYPE=MyISAM` 在现代 MySQL 是语法错误。** 老安装脚本里 58 处 `TYPE=MyISAM` + 1 处 `Type=MyISAM`，还有 `TYPE=Heap`。要改成 `ENGINE=InnoDB` / `ENGINE=MEMORY`，同时把文件编码从 GBK 转 UTF-8、文件头加 `SET SESSION sql_mode=''`。

转换时有三处"异常"全是误报：`TYPE=` 残留在自己的注释里、第 60 处 `ENGINE=` 是数据内容、中文行数为 0 是因为安装脚本本身就是空库结构。**批量替换之后一定要逐条核对这些"看起来不对"的地方。**

**短标签保护头会失效。** 备份文件开头常写 `<?exit();?>` 防止被直接下载读取。PHP 8 默认关闭 `short_open_tag`，这句保护头直接失效，备份变明文。

注意同一个项目里另一种写法仍然有效：`<?PHP exit(...)?>`——大写的 `PHP` 不是短标签。所以加固时**不能一刀切把所有 `<?` 都改掉**。

**行尾符会污染 diff。** 编辑工具把混合行尾统一成 CRLF，结果 `viewthread.php` 显示改了 100 行，实际内容只改 1 行。量化一下：真实改动 53 行、行尾噪音 88 行。修法是按内容匹配还原原行尾。

**字符集别从 dump 头部推断。** dump 开头的 `SET NAMES utf8` 是 mysqldump 客户端的连接字符集，不代表表字符集。正确做法是把 59 张表的建表语句全打出来看 `DEFAULT CHARSET`。顺带排除一个假象：用 `head -c` 截断 dump 看到的 `'�` 是多字节字符被切断的伪影，不是坏数据。

## 八、Windows 侧的老工具链

Delphi 7 那个客户端的任务是：界面中文化、加后台线程收发、切 JSON 协议、历史截断、代理令牌鉴权、配置从 ini 搬进注册表。技术含量不高，但工具链的坑一点不少。

**源码编码必须是 GBK (CP936) + CRLF + 无 BOM。** 窗体字体改「宋体」9pt、`Font.Charset = 134`（`GB2312_CHARSET`）。这些值我都是从用户给的 Delphi 7 源码 `Rtl/Win/Windows.pas` 里确认的——**老工具链的常量定义，宁可去查它的源码，别猜。**

**`TCanvas` 会偷偷重置 `BkMode`。** 切换字体后 `BkMode` 会被重置为不透明，`DrawText` 就用当前画刷（Logo 绘制遗留的白色）填充文字背景，形成一块白底。修法是封装一个统一的绘制函数，每次绘制前强制 `SetBkMode(TRANSPARENT)`，全文件 14 处文字绘制都换过去。

**Delphi 7 不允许在方法的 `var` 块之后定义嵌套过程。** 报 `Identifier expected but 'PROCEDURE' found`，还会级联出一堆看似无关的错误（`FMsgCount`、`pnlHeader` 未定义）。修法是把它提升为窗体私有方法。

**`.res` 头结构错了会连累 IDE 崩溃。** 我生成的图标资源报 "Invalid resource file"——因为 `.res` 头偏移 4 应为 `0x20`、偏移 8/12 应为 `0xFFFF`，而我生成的是全 0。对照官方 `WordPad.res` 字节修正后又崩了一次（`coreide70.bpl` AV）：原因是**加了 48×48 尺寸**，而 Delphi 7 时代的图标只含 32×32。改回 Win95 标准的 16+32 两个尺寸才稳定。

**没有编译器时的验证方式。** 所有 API 签名（`TThread.Create/Resume`、`TClipboard.AsText`、`ByteType`、`WideCharToMultiByte`、`SetWindowRgn`）都逐条回查 Delphi 7 源码原文；编码则用"GBK 可解码、UTF-8 不可解码"双向校验确认。编译只能交给装了 Delphi 7 的虚拟机。

## 九、容器与运行环境的三个细节

**rootless podman 里 `user=1000` 反而不对。** 容器内只有 `root` 映射到宿主用户，设 `user=1000` 会落到 subuid，写不了文件；改成 `user=0` 又会让 fpm 拒绝以 root 跑池进程。最终用 `userns_mode: keep-id`，容器内 uid 1000 = 宿主用户。

**php-fpm 的工作目录不是站点根。** 所有相对路径写缓存都会失败，要给池配置 `chdir`。

**nginx 会缓存 php 容器的旧 IP。** 改完代码不生效，重启 php 之后必须一起重启 nginx。

## 十、顺手补的安全缺口

- **`install.php` 的 nginx 配置只写了 allow/deny，漏了 `fastcgi_pass`**，结果 PHP 被当静态文件返回、直接泄露源码；
- **后台首页会自动删除 `install.php`**（Discuz 自带的安全特性），我在冒烟测试时把它删了两次才发现；
- **删了文件不等于删了历史**：`config.inc.php` 已经从最新提交删除，但数据库密码仍在 git 历史里，任何人 clone 都能看到。用 `git filter-repo` 重写历史、`git log -p --all` 复扫确认零命中，同时轮换口令；
- **错误处理路径本身也要脱敏**：把语言对象当字符串 `printf` 的那类 bug，访客看到的是带完整服务器路径的 Fatal 页。

## 总结

三次移植的共同结论，可以压成五条：

1. **能交给工具改的别手改**，但工具本身要验——我的第二版扫描器就改坏了 9 个文件；
2. **看起来像 bug 的地方先假设它是功能**，尤其那个"从不删除"的函数；
3. **编码约束要贯穿全程**：写文件、连数据库、发响应头，任何一环按 UTF-8 处理都会出现方块字；
4. **列宽、`sql_mode`、短标签、字符集这类环境前提，比代码错误更容易漏**——它们不会让 `php -l` 报错；
5. **"没有报错"和"没有问题"是两件事**。那 4186 条日志在修复前看起来像数据库故障，实际是白屏的副产品——错误日志本身也会骗你。

最后一句：环境要恢复到"未安装"状态再交付，让别人自己跑一遍安装向导。那才是真正的验收。
